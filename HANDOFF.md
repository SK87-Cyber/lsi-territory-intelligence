# HANDOFF — Southeast DOT Lighting Intelligence

Read this first in any new conversation. It explains how the site is built so you can extend it without re-deriving anything. `ROADMAP.md` says *what* to do next; this file says *how the thing is made*.

## 2. Working loop for a milestone

1. **Clone the repository** — `git clone https://github.com/SK87-Cyber/lsi-territory-intelligence` (or `git pull` an existing clone). Since Oct 27, 2026 the repository is the kit: template, logos, geometry, parsers, deltas, migrations and workflows are all committed, and nothing is uploaded into a conversation any more. (The old kit zips are retained under `archives/source-kits/`; see `docs/INFRASTRUCTURE.md` for GitHub → Netlify → Supabase.)
2. Read `ROADMAP.md` §0 and §2. The first unchecked milestone is the target; its scope is exact.
3. Edit `template.html` with `str_replace` (small, surgical edits — the file is big; never rewrite it wholesale).
4. Set the new build number in `BUILD`, then `npm run build` — this runs `build.py` and the full `verify.js` gate, exports `dist/snapshot.json`, and writes `dist/index.html`. (`python3 build.py <milestone> --out dist` + `node verify.js dist/…html` is the same thing by hand.)
5. `verify.js` must print `script executes: OK` and `RECONCILED` for every letting; `npm test` must pass. CI runs both again on push, and neither Netlify nor the database accepts a build that fails them.
6. Visual check with Playwright (installed): load the built file with `file://`, call `show('NC')` in `page.evaluate`, screenshot. Since 1.9a the geometry is embedded, so **real county boundaries render offline** — if you see the stylized fallback, `geo-se.json` is missing from the kit. Run `hover-check.js` too after any interaction change.
7. **Open the Method tab (formerly Roadmap) in the rendered page and read it.** It is part of the product and `verify.js` cannot check prose. In 1.11 it was still showing a retired requirement and a milestone count four builds behind. Reconcile it with §2 of `ROADMAP.md` before shipping.
8. Update `ROADMAP.md`: tick the milestone, refresh §0, append the audit trail, log decisions.
8b. Re-verify the personnel and phone numbers the run touched (owner rule, Sep 2, 2026 — a dated org chart beats an undated page; anything unverifiable is flagged "re-verify before outreach", never guessed).
9. **Snapshot the build being superseded** (`snapshot.py … --append snapshots.json`, re-embed `SNAPSHOTS`) so the what-changed panel is true. ## 3b. The layer model — read this before adding a state (build 2.1)

The platform is **twelve layers**, declared once in `LAYERS` near the top of the `STATES.forEach` block. Seven transfer to any state DOT; five are bid-derived and state-specific.

- **Registries** hold each state's data: `YEAR`, `PIPELINE`, `COMPETE`, `DIVACT`, `DICTS`, `OWNERSHIP`, `DECISION` — all keyed by state id. **Adding a state means filling slots, never editing render code.** If you find yourself editing a renderer to add a state, the layer is missing an abstraction; add it to `LAYERS` instead.
- **`has(s, "layerId")` is the only way a view asks whether a layer exists.** Never write `s.id==="XX"` for a data decision. Six `isNC` branches survive and all six are presentation specific to NC's Division map — leave them until a second state has the same need.
- **Coverage is computed, never declared.** Each layer carries a `has(s)` predicate that reads the actual data. The Overview coverage matrix, the per-state "what this model is built from" tile and the Roadmap tab's layer table are all generated from that one array. Do not add a hand-maintained status list anywhere; it will drift within one run.
- **A missing layer renders `missingCard(s, layerId, kicker)`** — states what the layer is and what would fill it. Never a zero, never a share of a budget. `verify.js` fails the build if a non-NC page emits `NaN`, `undefined`, `Infinity` or a `$0`.
- **The acceptance test is real, not a mock.** The seven non-NC states already are the "transferable layers only" case, so `verify.js` runs against them. It has been shown to fail (substituting a `$0` tile), which is the only reason to trust it.

**To add a state:** fill `STATES` (budget, basis, geo, chain, procurement, sources), add its territory rows to `GEO`, and add `OWNERSHIP[id]` and `DECISION[id]` from that state's roadway lighting policy. `OWNERSHIP[id].digest` = [who buys, one-sentence why] — it feeds the "Who buys lighting here" tile that replaces the third UNKNOWN card on any state with an ownership model but no bid data. `DECISION[id].kind` picks the render branch: default = standing committee (NC), `"distributed"` = jurisdiction + region, case-by-case (AL), `"conditional"` = the two-key gate, state warrant + local agreement, with a `gates` array of [road class, state key, local key] rows (TN). A state that fits none gets a NEW branch — never force a fit. Anchor the ownership panel on the highest-authority source available (statute > manual > policy > observed practice) and say which it is. `TERRITORIES[id]` (counties per region, validated against Census names) turns the state's map into the colored hover map; `OFFICES[id]` adds area/district office markers — both only from the agency's own published assignment, transcribed, never guessed. That is five of the seven transferable layers with no render changes. `PIPELINE[id]` follows if the state publishes a queryable STIP service. **The bid layer reopened on Sep 4, 2026** (owner: "Georgia first, bids after"), designed from all eight states' evidence. Reads go in catalogue order — Kentucky (3.9, anchor), Arkansas (3.10, control), then a decision on the rest — and every read is captured to the universal contract record in §5. Before reading a state, its `BIDSRC` entry must show what the four checklist artifacts are; a state missing one gets a labelled partial, never a verdict.

## 5. Adding an item-level read

### 5.0 The universal contract record (fixed in build 3.8 — every state's `YEAR[id]` is built to it)

Every field NC already carries survives; five are new (★). The Kentucky read is built to this from line one.

```
contract: {
  id, letting_date, call, state, channel ("central"|"district"|"local-let"),
  county[], territory (Division/District/Region label), tip_or_project_no,
  title, project_type ★ (the agency's own type string — feeds propensity scoring later),
  bidders: n (from the award artifact, never the tabs), low_bidder, low_amt, est, diff_pct,
  award: { status: "apparent"|"awarded"|"rejected", artifact, date ★, availability_date ★, completion },
  cls: "L1"|"L2"|"L3"|"LUMP"|"None"|"UNKNOWN",
  lighting: {
    identified,                                   // everything lighting, at the low bidder
    split: { hardware, infrastructure, work } ★,   // poles/luminaires/drive units/cabinets · conduit/feeder/JB/foundations/service · remove/relocate/reinstall
    range: [min, max] across bidders,             // only if every bidder's items are in the tab
    quantities: [{ class, qty, unit, wattage?, mount_ht? }] ★,   // "44 high-mast luminaires 335–560W", "6 × 120' standards"
    items: [{ line, code, section, desc, qty, unit, prices: { bidder: unit_price } }] ★   // keep EVERY bidder's line — price book, dispersion
  },
  evidence (with {ST-n} citation tokens), exclusions_applied[]
}
```

Rules that ride with it: `product` (NC's current figure) equals `split.hardware` and is kept for continuity; the bid layer is an **evidence and quantities layer, never a market-size instrument**; the ownership model sets each state's expected base rate (KY highest, AR lowest) and a finding that contradicts it means the dictionary is wrong, not the state; **every published figure carries its channel label** (Central / District / local-let). Derived views the record unlocks without further research: a per-state lighting price book, price dispersion on lighting items vs the contract, the submittal window (letting → award → availability), the retrofit rate (remove+install vs install-only), lighting propensity by `project_type`, and the annual letting-calendar strip.

**Reading a new state, in order:** (1) confirm its four `BIDSRC` checklist artifacts by opening one of each; (2) build the state's dictionary from *its* item master and spec section — never NC's codes; (3) parse one letting with a state adapter of `parse_bidtabs.py` (only the dictionary and the column map change); (4) run the two-classifier adjudication (code/section test ∪ naming test − exclusions, with the shared-electrical anchor rule); (5) reconcile every bidder's item sum to the printed total — a contract that does not reconcile does not publish; (6) award flags only from the award artifact; (7) fill `YEAR[id]` to the record above and let `has()` turn the layers on. Anchor-state expectations: KY tabs are description-keyed (no code column printed — key the dictionary on the standardised description plus the KYTC bid-item code list); AR tabs print a six-digit code whose first three digits are the spec section (714 lighting, 708 conductors, 710 conduit).

### 5.1 North Carolina (the reference adapter)

For a contract already in a letting object: set `cls` to `"L2"`, `"None"` or `"L3"`; add `l2` (sum of Division 14 items at the low bidder's unit prices), `l2range` (min–max across bidders), `product` (poles + luminaires + drive units + controls), `evidence` (item numbers, sections, exclusions applied). Append any new pay-item codes to `NC_RUN6.codes`. §1413 Portable Lighting and "WZ Presence Lighting" are excluded (temporary). Apparent values show in amber; nothing becomes confirmed until Item C prints AWARDED or minutes record the award. ITS camera mounts that borrow the word *luminaire* — "Luminaire Arm for Video System", "CCTV Metal Pole" — are excluded too.

**Read the spreadsheet, not the PDF.** The combined bid-tab PDF is readable only to a fixed depth — roughly the first two contracts of a ten-contract letting — so it can never finish a letting. The spreadsheet edition (`L<YYMMDD> XLS Bid Tabs.xls`, or `Bid Tabs YYMMDD.xls`, both on the bid-tabs index) carries every contract. `web_fetch` returns it as binary, so it has to be uploaded into the conversation or fetched by a download-capable tool. Then:

```
soffice --headless --convert-to xlsx --outdir x <letting>.xls     # legacy BIFF8 -> xlsx
python3 parse_bidtabs.py x/<letting>.xlsx                          # all contracts
python3 parse_bidtabs.py x/<letting>.xlsx --contract C205219       # one contract, full item detail
```

The sheet is one flat table: one row per (contract × item × bidder). Column map is in the script's docstring. It holds itemised prices for a *subset* of bidders (1–4 of as many as 11) and always includes the low bidder — so contract totals and bid counts still come from Item C, and a range quoted "across bidders" from the spreadsheet is narrower than the true range.

**The classifier is a union of two tests, and needs an anchor.** An item is lighting if its pay-item code is in the 5000–5299 family, *or* its spec section is 1400–1413, *or* its description says LIGHTING / LUMINAIRE / LIGHT STANDARD / HIGH MOUNT / LITE STD / LIGHT POLE / STREET LIGHT / LITE CNTRL outright — minus the exclusion list. Neither half is sufficient on its own: the code test missed `ELECTRICAL CONDUIT SYSTEM FOR LIGHTING` priced as a structures item (8860, $226,855 on C204773), and a naming test alone claims sign supports. Separately, shared electrical — duct (5150/5155), feeder (5175–5220), junction boxes (5240), service lateral (5125) — counts **only** when a lighting-specific item is present in the same contract; those codes serve signals and cameras too. A contract carrying shared electrical and nothing else is published as *not counted*, with its amount shown.

**Classification is structural, never by keyword alone.** An item is Division 14 when its pay-item code is in the 5000–5299 family or its spec section is 1400–1413. Keywords produce false positives that will publish wrong numbers: `SUPPORT, BREAKAWAY STL BM` is an S903 sign support and `SUPPORTS, OMNI-DIRECTIONAL BREAKAWAY` is a 4360000000-N signing item. Both are in the sample as regression cases.

**Completeness test.** Sum each contract's item rows by bidder; the low bidder's sum must equal the Board's Item C contract total. All 25 contracts in the June–August sample match to the cent. If a contract does not match, its item list is partial — do not publish a verdict for it.

**Class vs product.** Any priced Division 14 item makes a contract `L2` — conduit-only counts. What the money *buys* is a separate figure, `product`, identified by pay-item code family and never by wording: 5005/5010/5015 standards, 5020 drive unit, 5030 high-mast luminaire, 5080 light standard with luminaire, 5120 service pole, 5145 control cabinet, 5260 generic lighting lump sum. Foundations (5025, 5070), service lateral (5125), duct (5150, 5155, 5265), feeder (5175–5220), junction boxes (5240) and remove/relocate/reinstall work (5270) are infrastructure or labour. Wording rules fail here — NCDOT writes a light standard with a luminaire as `LITE STD LUM`.

**`LUMP`** is a bid that was never itemised — a design-build lump sum carrying ≥ 50% of the bid. It is not `None` (which means the items were read and held no lighting) and not `L3` (which asserts lighting scope *is* confirmed). Lighting inside a design-build contract needs the plans or the submittals; the tabulation will never show it.

## 6. Sources that work, and how

- Bid tabulations: `https://connect.ncdot.gov/letting/pages/bid-tabs.aspx` → `Bid Tabs YYMMDD.pdf`. A single fetch with `text_content_token_limit` ≈ 22000 returns ~5 contracts of items. The first contract in each PDF is the cheapest read.
- Awards: Board of Transportation **Item C** — live at `.../Documents/ItemC.pdf` (URL reused monthly; pre-meeting = recommendation, not award); archived at `.../Archive/YYYYMM_MeetingArchive.pdf` (Item C is first) and `.../Archive/YYYYMM_Minutes.pdf` (award statement). Index: `https://www.ncdot.gov/about-us/board-offices/boards/board-transportation/Pages/archives.aspx` — that host; an `ebs.ncdot.gov` guess fails DNS. The August 6, 2026 minutes carry the July letting award statement. Fetch archives with limit ≈ 9000.
- **Pipeline: query the STIP, don't scrape it.** The adopted STIP is a map service — `https://gis11.services.ncdot.gov/arcgis/rest/services/NCDOT_STIP/MapServer`, layer 0 points and layer 1 lines, fields `TIP, Route, Description, Category, RightOfWayYear, ConstructionYear, ProjectCost, Counties, Divisions`. Lighting scope in one query per layer:

  `.../MapServer/1/query?where=Description%20LIKE%20%27%25LIGHTING%25%27&outFields=*&returnGeometry=false&f=json`

  Two fetch gotchas: `outFields` with a comma list is rejected by the proxy — use `outFields=*`; and `UPPER(...)`, parentheses or an `OR` in the where clause are rejected too — run one condition per query. `returnCountOnly=true` first, so you know how many features to expect and can tell a real answer from a truncated one.
- Pipeline delta: the STIP layer is a dated snapshot, so read the Board archive's Items H/K/L/M/N forward from that date for what has been funded since. HL-0154 exists only there, not in the STIP.
- NCDOT directory (public): `apps.ncdot.gov/dot/directory/authenticated/UnitPage.aspx?id=621` (Chief Engineer), `?id=681` (Roadway Design incl. Lighting & Electrical). Emails are behind icons — link, never guess.
- Bid tabulation URLs follow `https://connect.ncdot.gov/letting/Central%20Letting/<MM-DD-YYYY>%20Central%20Letting/Bid%20Tabs%20<YYMMDD>.pdf` — note June's is `Bid Tabs 260616 Post.pdf`. The `bid-tabs.aspx` index lists a PDF and an XLS per date; the letting folder itself is robots-disallowed.
- Proposals/plans: `connect.ncdot.gov/letting/letcentral/...` requires a signed-in session. Blocked; noted in the roadmap. `bidx.com/nc/lettings` (the AASHTOWare portal) redirects to a login and is blocked the same way.
- `web_fetch` only accepts URLs seen in a prior search/fetch result. Search first.

## 7. Rules that must survive every conversation

- Build number = Phase.Milestone reached; letter suffix for a fix that delivers no milestone.
- Nothing in the product references runs, phases-in-progress, workstreams, or "not yet" states except the honest `UNKNOWN` / "Not yet read" labels.
- No manufactured numbers: L3/L4 never in totals; apparent ≠ awarded; QPL ≠ installed; vacancies stay vacant; emails never guessed.
- Every displayed figure traces to a numbered source.
- Update `ROADMAP.md` last, every time.
- **The model is twelve layers, seven of which transfer to any state DOT** (programme size, territory model, leadership chain, ownership/funding model, decision body, programmed pipeline, procurement mechanics) and five of which are bid-derived and state-specific (item reads, identified dollars, dictionary/classifier, competition, award confirmation). A state's bid-derived layers turn on only when its letting has been read and reconciled — the catalogue entry alone never counts as coverage.
- **Never reuse NC's lighting dictionary in another state.** Pay-item family 5000–5299 and spec sections 1400–1413 are NCDOT numbering. Applying them elsewhere returns zeros that look like answers. The method transfers; the codes do not.
- **Read the ownership and funding policy before reading any lettings in a new state.** In NC it explained the entire letting record — DOT-funded lighting is an interchange and freeway product line, and everything else is municipal. Question order: who owns and funds → which roads qualify → who approves → what is programmed → what has been let.
